# 功能模块详细拆解

全景、横向比较和首次安装包分析时使用本规范。专题分析按用户指定范围应用相同深度要求。

## 能力地图

先为每个产品建立“产品、功能模块、子功能”三层结构，再追踪跨模块任务。模块围绕用户要完成的事情划分，例如拍摄、素材编辑、结果交付、账号权益；名称和层级随实际产品调整。

- 一个子功能要对应可描述的用户动作或结果，名称具体到“批量加水印”“选择导出格式”等程度。
- 导航入口、状态变体和技术组件可以帮助识别能力，但不直接按代码目录、SDK 或图标建立产品模块。
- 同一能力的多个入口归到同一子功能；真正不同的任务或规则分别拆开，避免重复统计。
- 确认的常规能力也应进入功能正文。摘要筛选最重要的发现，详细能力地图负责完整覆盖有意义的用户任务。
- 只有局部线索的能力保持待确认状态。未从材料确认的能力不能直接写成产品没有这项功能。

## 每个子功能要讲清什么

材料支持时，至少讲清用户场景、入口、主要动作和结果。下表按功能实际需要补充，不要求每个小功能填满所有项。

| 内容 | 要回答的问题 |
|---|---|
| 用户和场景 | 谁在什么情况下使用，完成什么任务？ |
| 入口和前提 | 从哪里开始，需要哪些素材、账号、权限或已有数据？ |
| 主流程 | 按先后顺序做什么，系统在哪一步自动处理，用户在哪一步选择或确认？ |
| 输入与结果 | 输入什么，生成什么，能否保存、分享、继续编辑或进入下一模块？ |
| 业务规则 | 默认值、可修改项、批量范围、数量限制、时效或格式限制是什么？ |
| 状态与补救 | 加载、空内容、成功、失败、取消、重试或部分完成怎样影响任务？ |
| 权益条件 | 哪些步骤受登录、角色、会员、广告或收费限制？ |
| 模块联系 | 与上一步和下一步如何衔接，数据是否复用，是否形成重复使用的理由？ |
| 产品含义 | 具体省了哪一步、降低了什么成本、有什么代价，适合什么情况下借鉴？ |

不要把“支持编辑”“提升效率”“操作便捷”当成完整拆解。具体说明能编辑什么、如何完成、结果是什么；只有材料支持时才写价格、配额、算法效果或真实使用表现。

全局账号、权限和通用规则集中说明，各子功能只展开自己的差异。重要异常路径写出恢复动作；仅出现“失败”字样时，不补写不存在的自动重试、恢复或容错机制。

## 按模块组织报告

每个重要模块用以下结构组织，按内容选择表格、流程和文字：

1. 模块解决的任务及主要使用者。
2. 子功能表，说明每项怎么用、得到什么结果和关键限制。
3. 核心用户流程，按入口、操作、处理、结果、下一步展开。
4. 影响任务完成的规则、状态和权益条件。
5. 与其他模块的联系和具体产品判断。

简单模块可以合并其中几项；复杂模块可继续拆成多个子流程。以用户能理解真实用法为完成标准，不按固定字数、功能数量或页面数量凑内容。

横向报告先展示各产品的模块详情，再用同一用户任务对齐差异。比较完成步骤、可控制内容、结果可用性、付费门槛与补救路径；对缺少材料的产品说明范围，避免把未知当成能力缺失。

HTML 的目录、卡片和留白负责阅读节奏。详细内容可以分成多个模块章节或子标题，功能正文不因摘要需要简短而被删减。正文继续遵守不展示材料出处和技术文件路径的要求。

## 深度示例

以“批量处理照片”为例，逐步检查：从哪个相册入口选择照片，如何选用统一设置，哪些内容可逐张调整，处理过程中有什么状态，处理失败后能做什么，完成后如何保存或分享，以及哪一步涉及付费。

报告只写实际确认的部分。若收费资格未知，说明这个具体问题；不要据此省掉已经弄清的选择、处理和保存流程。

## 快照记录

详细拆解的结果要进入 `state.json`，供下次版本比较复用：

- `modules`：每个模块记录稳定的 `id`、`name`，可补 `parent_id`、`purpose`、`related_ids`。
- `features`：每个子功能记录稳定的 `id`、`name`、`status` 和所属 `module_id`。
- 已明确的细节按需写入 `purpose`、`scenario`、`entry`、`conditions`、`journey`、`states`、`inputs`、`outputs`、`rules`、`access`、`related_ids`、`interpretation`。这些字段可以是简短文本或结构化列表，不给未知字段编造内容。

标识按稳定的用户能力命名；界面换名、文件迁移或入口调整时继续沿用原标识。快照只供内部版本比较，页面展示面向读者的描述。
