# 版本监控

## 基线与身份

每次报告内嵌 `digital-product-competitor-research` 快照，含产品标识、平台、版本、包哈希、文件清单和人工确认的功能状态。横向报告将每个产品的快照合并在同一 HTML 中，后续可单独更新其中一个产品。压缩快照只供后续研究读取，不在页面展示。旧 HTML 是可携带的历史基线；同目录存在多个报告时，按产品标识、平台与版本选择最新且可匹配的一份，不凭文件名猜测。

核对包名或 Bundle ID、签名或发行方、主程序、组件重合度与产品名称。包标识变化时调查客户端换轨；重合度低时当成两个客户端比较。仅凭版本号相近不能视为连续升级。

## 比较顺序

1. 用 `report.py find-baseline` 搜索同产品同平台的旧 HTML，再用 `extract` 读取快照。读取失败时检查是否有旧安装包；不要伪造历史基线。
2. 扫描新版并建立完整候选池。先用 `report.py diff` 看文件的新增、消失、变更和组件分布，只将结果用作调查入口。
3. 对异常密集的新资源簇、旧能力信号大量减少的区域和未归类变化逐一复核。追踪入口、动作、状态和结果；检查改名、模块搬迁、远程页面、资源合并及代码重构。
4. 为每项变化标记：确认新增、原有增强、确认移除、视觉刷新、工程迁移、能力储备、客户端换轨。还原新旧用户路径后再写“变化意味着什么”。
5. 将新版完整快照嵌入新版 HTML。下一轮以此为新基线，保留旧报告以便多版本追溯。

## 报告重点

版本报告先写最重要的用户变化，再写产品方向判断和本品可能的验证动作。没有重要用户变化时直说，并说明主要改动集中在哪些层面。文件数量、路径数量和 SDK 名称只能辅助判断变化规模，不能充当功能价值。

同一工作目录可自动发现旧 HTML。跨工作目录、换机器或旧文件丢失时，用户需要提供旧 HTML 或旧包；仅有新包只能做该版本的全景研究。不得把宣传更新说明直接当作包内已验证功能。
